Executive recommendation

Use a targeted architectural refactor, with a redesigned review screen. A whole-app rewrite is not justified by the evidence so far. Keep the pure diff/analysis models, adapter seams, test fakes, and terminal lifecycle. Replace the parts that let screen state, jobs, persistence, and rendering drift apart.

The product already asks the LLM for much of the right material: a summary, inferred intent, risks, grouped reading order, and per-file notes. The missing piece is a coherent reading experience: “What am I reviewing? Why start here? What should I verify next?”

First fixes: real Checks/Discussion navigation, dependable draft/job ownership, and consistent filtering of the exact LLM payload. Then shorten and integrate the assistant’s explanation; optimize rendering and the terminal-test harness around measured costs.

Passing checks establish a useful baseline, not product completeness. Several findings below are observable despite the green suite.

Keep and strengthen

  • One thread owns mutable application state.
  • Explicit effects and job IDs for background work.
  • Pure parsing and normalization with offline fakes.
  • One action registry for default keys and generated help.
  • Managed workspaces, batched review submission, and terminal restoration.

Refactor around ownership

  • ReviewSession: repo, PR, revision, draft, analysis and review progress.
  • ReviewTab separate from FocusedPane and text-entry mode.
  • A typed job registry: owner, generation, status, cancellation and result.
  • Runtime services own IO; reducers return effects; renderers borrow prepared view data.
  • One immutable context manifest for inspection, analysis and chat requests.
The recurring failure pattern is lifecycle coupling. Opening a new PR replaces detail without replacing the whole review session. Patch completion reloads drafts. A bundle can be labeled with the PR current at completion rather than its origin. Cancellation is spread across separate job slots. Fixing isolated handlers will keep producing variants of the same bugs; make the review subject and generation explicit across all related state and effects.

2. User experience: guide the reading, keep the code visible

The desired five-minute journey

  1. Open a PR: see the author’s description, changed-file count, CI status, and discussion count. Cached content appears immediately; refresh is visibly separate.
  2. Start a guided review: select a model if needed, see the request estimate, then get a two-sentence brief. Browsing remains usable while analysis runs.
  3. Read a suggested sequence: each step has a human name and one sentence explaining why it comes now. The current file never jumps away when the plan arrives.
  4. Review the code: “What changed / Why, inferred / Verify” stays beside the current file. Open details only when needed. Mark a file reviewed or leave a local comment.
  5. Finish: inspect CI and unresolved discussion, read the draft, then use one explicit publish confirmation with the exact destination and content.

The tab labels, counts and actions should come from the same tab model used by keyboard dispatch, mouse hit-testing and rendering. At 80×24, use full-width tabs and a collapsible file list; keep the current-file explanation to a few lines.

Better LLM output, less prose

  • Brief: two sentences about the PR.
  • Per file: one short “what”, one “why” explicitly marked as inferred, and up to two concrete things to verify.
  • Plan steps: action-oriented names such as “Establish the retry contract”, not only directory names.
  • Evidence: clickable known paths; invalid or unsupported claims are kept out of the actionable risk list.
  • Coverage: distinguish analyzed, truncated, unclassified, and reviewed-by-the-human.

A reading order that fits the change

The current prompt always puts tests and docs last. That is often a poor fit for a behavioral change, schema migration, or contract-first PR.

Ask for dependencies and a short rationale, then group implementation with the tests that explain it. Start with contracts, examples or design notes when they establish intent. Put generated files and mechanical churn later, visibly included.

Current behavior: src/domain/analysis.rs:1043–1045; fallback taxonomy: src/domain/plan.rs:87–179. This is a proposed product change, not a claim that arbitrary AI reordering is more accurate.

3. Bugs and trust gaps

P1 Fix before broad rollout. P2 Next iteration. Reproduced means a fixture/probe exercised the behavior; code-proven means a concrete source path establishes it; speculative performance risks are separated below.

P1 · F01 Excluded file contents can still leave through the diff Reproduced

Impact: the context inspector can say a .env file is excluded while the outbound prompt still contains its changed lines. Analysis and chat use the same vulnerable bundle builder.

Reproduction: parse a patch changing .env, pass its full file bytes to build(), and use a synthetic sentinel. The file segment is excluded, but bundle.text still contains the sentinel from the diff.

secret_file_marked_excluded=true
secret_diff_sentinel_still_in_outbound_bundle=true

Fix: enforce one content policy across all representations, including old/new rename paths, deleted-file hunks, full file bodies and added context. Build the manifest from the actual filtered payload. Test the final text delivered to the fake LLM.

Evidence: src/domain/context.rs:185–205,391–410,611–674; unfiltered patch supplied by src/tui/app.rs:3071–3080. Related: FR-4.6, NFR-3.1. No real credential or provider was used in this probe.

P1 · F02 Configured LLM spending limits are not reliable ceilings Reproduced + code-proven

Impact: selecting a large-context model can make the request much larger than the configured max_context_tokens. Documented per-selection temperature and max_tokens are not carried through ResolvedSelection into the analysis/chat request builder.

configured_context_tokens=100000
catalog_context_tokens=1000000
effective_context_tokens=967232

The helper chooses the catalog limit instead of taking the smaller configured ceiling. analysis_chat() uses the catalog/default output cap; a user’s 4,096-token setting does not drive it. This is request-sizing behavior, not a measurement of actual provider billing.

Fix: carry the user’s effective settings in one request configuration; use a clearly defined minimum of model capacity and user budget, reserve output/system/history overhead, and show effective limits before sending. Keep advisory model metadata distinct from user-selected ceilings.

src/application/models.rs:213–232,351–373,409–452; src/tui/app.rs:1457–1468,3053–3067; documented knobs: docs/configuration.md:30,63–64. FR-4.6, FR-4.7, FR-5.4.

P2 · F03 Ambiguous basenames attach AI notes to the first matching file Reproduced

Impact: in a Rust PR changing multiple mod.rs files, a model’s bare mod.rs reference can be linked to the wrong module.

Reproduction: build PathIndex from changes to src/a/mod.rs and src/b/mod.rs. resolve("mod.rs") returns Some("src/a/mod.rs") instead of rejecting ambiguity. The alias created for the first file is not removed after a collision.

Fix: build exact paths first; add basename aliases only after counting all candidates. Require full paths on ambiguity. Keep explicit canonical paths and rename aliases separate.

src/domain/analysis.rs:284–323,360–369. FR-4.1: evidence must point to the correct changed file.

P2 · F04 The context byte cap can be exceeded by its own formatting Reproduced

Impact: near a model’s context boundary, headings and placeholders can exceed the advertised budget. The builder measures body bytes before adding wrappers and appends placeholders without reserving their cost.

Reproduction: an eight-byte policy, eight-byte metadata and two binary placeholders produce an 82-byte bundle. This tiny boundary case demonstrates a broken invariant; it does not quantify typical PR overhead.

Fix: account for final serialized text before append; cap placeholders and segment wrappers too. Separately reserve prompt framing, chat history and output space. Assert that every constructed bundle stays within its byte-equivalent budget.

src/domain/context.rs:439–503,520–578. FR-4.6.

P2 · F05 “Shared context” differs between analysis and chat Code-proven

Both features call the same gatherer, but only ChatSpec supplies user-added paths. AnalysisRequest falls back to an empty ContextSource::added(). A fresh analysis gather therefore omits files added with :context add, while a chat gather includes them.

Fix: define a single revision-bound ContextSpec used by both features and the inspector. Include its fingerprint in the analysis cache identity so changing relevant context cannot silently serve an old answer. Preserve a clear display of what was actually analyzed.

src/application/context.rs:53–55,140–152; src/application/analysis.rs:65–78,98–118; src/application/chat.rs:116–148; src/tui/app.rs:1472–1488,3071–3080; cache key: src/ports/analysis.rs:30–45. FR-4.6, FR-5.3.

P1 · F06 Checks/Reviews and the numbered “tabs” are nonfunctional Reproduced

This directly explains the reported navigation problem. The header always selects [1 Diff]; Checks, Reviews and Analysis are explicitly rendered unavailable. Number keys and header clicks have no tab-routing implementation.

Reproduction: open a fixture PR; press 2 or 3, or click the Checks label. The number is reported as unbound and Diff remains. Existing discussion uses Spacepc; chat uses Spacec; analysis uses Spacea. These are different routes, not working tabs.

Additional mismatch: “5 Analysis (x, y)” is populated from approval/request-changes counts. The current snapshot-style test asserts the labels exist, not that their destinations can be reached.

Fix: implement the shared tab model first. Checks should show names, outcomes and a link to the GitHub Actions/check run; detailed log fetching can remain a separate product decision. Discussion should include reviews, inline threads, outdated threads and top-level conversation.

src/tui/components/review.rs:73–97,730–735; src/tui/app.rs:3838–3847; src/tui/keymap/mod.rs:335–428. G2, FR-2.4, requirements §5.2.

P1 · F07 Recommended order does not drive keyboard review navigation Reproduced

Impact: the main review flow can skip the next recommended file even though the tree advertises that order.

Reproduction: patch order is application → domain → TUI; recommended order is domain → application → TUI. Select the domain file, then press }. It jumps to TUI, skipping the application file that should come next. Cross-file hunk movement and ordinary diff scrolling also use original rows.

Cause: applying the plan rebuilds only the tree. The flattened diff rows stay in patch order, and movement scans those rows.

Fix: use stable file IDs plus a separate effective-order index shared by every navigation path. Preserve the underlying diff and current file. Test the journey across files, not only the tree’s sorted labels.

src/tui/diff_view.rs:320–324,377–399,590–624. G4, FR-3.5, FR-4.2.

P1 · F08 Visible focus and comment targets disagree with input Reproduced

Three related defects:

  • Wrong text destination: open a line comment, type X, Tab to Chat, type Y. The comment becomes XY; chat is empty. Draft composing takes precedence without checking focus.
  • Invisible cursor: at 160×40, open Chat, return focus to Diff, move down 23 rows. The probe had cursor=23, scroll=0, viewport=34, although the smaller diff pane did not display the selected source line. Comment creation can therefore target an invisible line.
  • Wrong split-view click: move to unified row 12 in split mode and click the first displayed diff row. The cursor goes to row 0. Rendering uses split coordinates while clicks use unified scroll coordinates.

Fix: compute layout once and share rectangles and visible-row mappings with rendering, scrolling and hit-testing. Model comment input and chat input as separate focus targets; only the focused input accepts text. These bugs can put a reviewer’s words on unintended code, so they deserve P1 treatment.

Input: src/tui/app.rs:1727–1733,4253–4257,4274–4277, src/tui/update.rs:897–907. Viewport: src/tui/app.rs:3882–3910, src/tui/components/review.rs:39–47. Split clicks: src/tui/diff_view.rs:464–475, src/tui/app.rs:3807–3810. FR-3.3, FR-6.2, FR-7.5.

P2 · F09 Discussion and overlays do not own their scrolling Reproduced

Reproduction: open a 12-comment conversation. Comment 12 is selected but the first comment is visible. Pressing k changes selection without scrolling it into view. Wheel over the popup: the diff underneath moves from scroll 0 to 3 while discussion stays at 0. Clicking a displayed comment moves the hidden diff cursor from 3 to 15.

Cause: discussion opens at the newest index with a zero offset interpreted as “from the top”; selection changes do not ensure visibility. Mouse routing ignores the active overlay and targets base panes.

Fix: topmost overlay first, then active tab, then focused pane. Keep selection visible and provide wheel/page navigation on the actual list. Preserve the underlying review position when dialogs close.

src/tui/discussion.rs:36–39,50–58; src/tui/components/conversation.rs:65–66,101; src/tui/app.rs:3712–3724,3736–3750,3768–3847,5021–5028. FR-6.4, FR-7.5.

P1 · F10 Draft anchors are silently moved to a new commit Code-proven

Impact: an old inline comment can be submitted against new code at the same line number, with its drift warning erased.

Reproduction to add: stage a comment at line 31 on head H1; change the PR to H2 so that the intended line moves; reopen or publish. Loading calls anchor_to(current_head), which overwrites H1 with H2 without translating lines. Publish does it again, and the adapter uses that new SHA as commit_id.

Fix: preserve the original commit for a nonempty draft. Require a validated re-anchoring transition when head changes; show old/new context. Bind submission to a snapshot of draft version and revision, not whatever is current when a handler executes.

src/tui/mod.rs:933–938; src/tui/drafts.rs:519–524; src/tui/app.rs:2304–2305; src/adapters/gh/review.rs:30–40. FR-6.3, NFR-3.4. Schedule described here was not run against GitHub.

P1 · F11 Changing PRs does not replace the whole review session Code-proven

Impact: chat can cross PR boundaries, local workspace support can get stuck on the first PR, and late jobs can apply to the wrong subject.

  • Chat: chat on A, then open B with no saved conversation. Closing A leaves the session; a load with None does not clear it. B’s request can use A’s history and persist into A’s session.
  • Workspace: A’s workspace remains Some and its successful job ID stays nonzero. Creation for B/new head requires no existing workspace and job ID zero, so B stays in remote mode. Readiness checks only head SHA, not PR/base identity.
  • Stale jobs: opening B replaces the detail job but not all related job IDs. Delayed A patch/context results can still match their slots. Some gathered bundles are labeled with the subject current at completion rather than their request origin.

Fix: atomically switch a revision-bound ReviewSession. Every job and continuation carries repo, PR, revision and generation; acceptance checks that identity. Store chat by its explicit session owner. Cancel or detach old work, and never retag its data with the new screen’s identity.

Lifecycle: src/tui/app.rs:1125–1134,1166–1171,1243–1255,1472–1507,2503–2517,2574–2591,2718–2721,3354–3366,3452–3454,4534–4537. Workspace scheduling: src/tui/mod.rs:407–439. FR-3.1, FR-5.1, ARCH-5.

P1 · F12 Canceling a remote submission can enable duplicate posting Code-proven

Impact: the UI says “the review was not sent” even when GitHub may already have accepted it. For a reply, Esc cancels the wrong worker slot, so the original request can continue while retry becomes available.

Reproduction to add: use a fake forge that accepts a POST but delays its response. Submit a review or reply, press Esc, and retry. The common cancel effect targets Slot::Review; replies use Slot::Post. Killing a local process does not undo a server-accepted request.

Fix: distinguish cancellable reads from remote mutations. After dispatch, interrupted transport means outcome unknown; reconcile before retry. Track the exact submission/draft version and mutation kind independently from the current modal. Keep explicit confirmation and dry-run behavior.

src/tui/app.rs:4951–4952; src/tui/mod.rs:967–975; src/tui/jobs.rs:292–294; src/adapters/process.rs:492–497; src/application/drafts.rs:100–109. FR-6.3, FR-6.5. An in-flight Enter guard exists; durable idempotency/reconciliation does not.

P1 · F13 A background diff reload can erase an open comment composer Code-proven

Reproduction to add: open a PR, start typing a comment in the initial remote diff, then release the delayed local-workspace diff. Every patch completion requests LoadDraft; reopening the draft clears the composer, pending post, selection and publishing state.

Impact: unsaved text disappears because unrelated background work finished. A reload during posting can also reset its in-flight guard.

Fix: load a draft once per session identity. Updating the diff must reconcile anchors while preserving the active composer and submitted snapshot. Treat disk loading, diff updating and draft editing as distinct state transitions.

src/tui/app.rs:3465–3467; src/tui/mod.rs:933–935; src/tui/drafts.rs:331–345. FR-6.1, FR-6.2.

P1 · F14 Reused workspaces calculate a different merge base Code-proven

Fresh workspaces use <remote>/<base>, but reused ones pass the bare base branch to git merge-base. An out-of-date local main can therefore make upstream changes appear as PR changes on reopening. A missing local branch can force unnecessary recreation.

Reproduction to add: keep local main behind origin/main, with the PR based on the newer remote main. Compare first materialization with reuse on a diff-cache miss. Their merge bases should be identical.

Fix: resolve and store explicit base/head/merge-base object IDs under the app’s workspace identity. Reuse must validate the same inputs as initial creation; avoid branch-name ambiguity.

src/adapters/git/worktree.rs:160–163,229–235,269. FR-3.2.

P1 · F15 LLM fallback eagerly executes both streaming methods Code-proven

Impact: for a backend supporting both methods, one user request can produce a second provider request, delayed completion, mixed preview text and incomplete usage accounting. The actual extra billing depends on the provider; it was not measured here.

let attempts = [
    Self::stream_structured(...),
    Self::stream_strings(...),
];
// Both have already executed before the result loop begins.

The early return for a successful structured response, partial failure or cancellation happens only after array construction. It cannot prevent the second call.

Fix: evaluate fallbacks lazily, one at a time. A fake supporting both streaming APIs must observe zero calls to the second after success or a partially emitted failure. Keep counters for every request and usage event.

src/adapters/llm.rs:596–628; existing coverage checks the plain fallback rather than the second streaming call at 1084–1100. FR-4.4, FR-5.2, FR-5.4.

P1 · F16 HTTP cancellation does not interrupt a stalled await Code-proven

Impact: canceling a stalled LLM connection can stop the visible spinner while leaving a worker occupied until the next chunk or timeout. Four occupied workers can delay unrelated jobs.

The structured and string streams await the initial response and next chunk before checking cancellation. Plain completion awaits the whole response. Queued deltas can also change a stopped pane back to Streaming because some cancellation paths retain its job ID.

Fix: race response and stream futures against cancellation, including before the first byte and between chunks. Release worker slots promptly; invalidate the canceled generation before queued updates are applied. Test with controlled pending futures, not long real sleeps.

src/adapters/llm.rs:229–238,279–284,323–329; src/tui/jobs.rs:55,1065–1071; src/tui/app.rs:1587–1595,2966–3023,3135–3138. Catalog fetch has a related 30-second noncancelable wait at src/adapters/http.rs:77–101. Cancellation latency was not timed.

P2 · F17 Durable user state needs a stronger storage boundary Code-proven
  • Concurrent writes: all atomic replacements of a document use the same <filename>.tmp. Two app instances can open the same inode, rename it, and continue writing into the now-published destination. Unique temp names prevent this interleaving; per-document serialization/versioning is still needed for logical lost updates.
  • Disposable chat: sessions live under cache/chat; deleting cache deletes user-authored conversation. Manual order overrides also live with analysis cache.
  • Session/index crash window: a session is written before its index. If the process dies between them, a still-valid old index hides the new session from normal discovery.

Fix: keep chat, draft and manual review state in durable directories. Use unique atomic temporary files and recoverable indexes; serialize saves per document with revision acknowledgments. If power-loss durability is promised, define and test directory fsync behavior too.

src/adapters/fs.rs:30–52; src/adapters/draft_store.rs:73–85; src/adapters/chat_store.rs:42–47,73–79,145,223–228; src/adapters/analysis_cache.rs:3–5. FR-8.5, NFR-4.1. Concurrent-writer impact depends on multiple instances sharing a home.

The slow tests are mostly terminal orchestration

CI currently repeats three format gates, three full Clippy gates, three full all-feature Rust suites, and eight Cargo build commands, plus filtered tests. Cached build invocations may be cheap; repeated test coverage is still redundant.

The PTY driver already waits for visible screen patterns, so this is not an entirely sleep-driven suite. But M4/M5 also request three-second settling sleeps for empty waits, plus an unconditional shutdown settle.

The harness also has correctness gaps

  • Unmet readiness/step waits print diagnostics but execution continues and the driver returns zero (drive.py:198–218,252). Shell assertions may catch some misses, but the driver itself must fail.
  • The M4 “in-flight extra Enter” test waits for “review posted” before its extra Enter (m4.sh:462–468), missing the interval it claims to cover.
  • The “thousand frames” performance test slices 40 rows repeatedly; it does not draw frames, and parsing is outside its timer (src/tui/diff_view.rs:2074–2096).
  • Every polling pass decodes and replays the entire capture (drive.py:119–125), with remaining-string copying at escapes (screen.py:108–110,144–146).

Synthetic replay measurements at 160×40: 17 KB → 4.50 ms, 85 KB → 28.50 ms, 170 KB → 70.53 ms, 340 KB → 188.27 ms (median of three). These benchmark the Python helper on generated terminal data, not the app or a complete validator.

A faster, stronger testing approach

  1. One CI gate per concern: fmt, Clippy, offline Rust suite, build. Let standalone validators accept a prebuilt/scenario-only mode.
  2. Deterministic scenario runner for breadth: dispatch real key/mouse actions into the reducer with fake ports, injected time and controlled completion queues. Assert both state and rendered output after each transition.
  3. Adversarial schedules: A→B PR switch with A finishing last; cancel with a queued delta; force-push with a staged comment; patch arrival while typing; POST accepted before response loss; save v2 completing before v1.
  4. A small PTY smoke suite: terminal enter/restore, actual key/mouse decoding, remote→local transition, streaming/cancellation, publish/reply payloads and dry-run, external editor. Keep local fixtures.
  5. Observable synchronization: wait for specific UI states, fake request counters or fixture completion markers. Fail immediately on timeout. Replace empty settles rather than merely shortening them.
  6. Incremental terminal replay: retain parser state and feed only new bytes, carrying incomplete escape/UTF-8 fragments. Keep raw captures for diagnostics.
  7. Actual performance tests: include render, reducer, long lines, folds, threads and streaming on the 400-file/10k-line fixture. Track p50/p95; avoid brittle microsecond CI gates.

No new dependency is necessary for the first version. The existing fake ports, Ratatui TestBackend, std/Tokio and Python are enough. Do not parallelize the current validators unchanged: fixed temporary paths and M1’s broad pkill can interfere with sibling runs. Isolate paths and target owned child PIDs first.

Visible progress is part of responsiveness

  • Show the current phase, elapsed time and a cancellable job label immediately.
  • Distinguish “queued”, “fetching”, “building context”, “waiting for model”, “streaming” and “saving”.
  • Use an indeterminate spinner when the duration is unknown; use counts for files and checks when real counts exist.
  • Keep existing content readable during refresh; preserve file, cursor and scroll position.
  • A canceled request must stop updating its view. A submitted mutation may need reconciliation rather than a claim that nothing happened.

Concrete acceptance budgets

  • Normal navigation: target p95 input-to-frame under 50 ms.
  • Busy state appears within one frame; no synchronous filesystem/process work on input paths.
  • Cancellation acknowledgment under 200 ms for read/LLM jobs.
  • Large-diff benchmark: 400 files / 10,000 lines, plus long chat and discussion.
  • Warm Rust tests: keep below 5 s on the reference machine. Set a separate, measured terminal-smoke budget.

Targets for the improvement work; runtime latency and cancellation SLAs have not been comprehensively measured in this audit.

Yes: simplify REQUIREMENTS.md and PLAN.md. Together they contain 1,400 lines. They mix current functionality, completed implementation history, proposed decisions and stale acceptance checkboxes. Meanwhile, the architecture doc still calls domain/application “empty” and describes M0.
